## 2. 반드시 지킬 Git 규칙

1. 작업 전에 `docs/README.md`와 해당 영역 문서를 끝까지 읽습니다.
2. `develop`과 원격이 같은지 확인한 뒤 기능마다 새 `feature/*` 브랜치를 만듭니다.
3. 원격에 같은 이름의 브랜치가 있을 수 있으므로 시작점을 명시합니다.

   ```powershell
   git switch develop
   git pull --ff-only origin develop
   git switch -c feature/<고유한-기능명> origin/develop
   ```

4. 기능·정리·병합 커밋 메시지는 모두 한글로 작성합니다.
5. 관련 검증과 전체 검증을 통과한 뒤 `--no-ff`로 `develop`에 병합하고 push합니다.
6. 병합된 로컬 기능 브랜치는 삭제합니다.
7. `feature/yj-work`와 `origin/feature/yj-work`는 팀원 작업 브랜치이므로 수정·병합·삭제하지 않습니다.
8. `origin/feature/growing-space-design-refresh`는 이미 존재하며 디자인 원본 이미지 커밋을 포함한 원격 브랜치입니다. 같은 이름으로 새 브랜치를 만들면 Git이 해당 원격 브랜치를 시작점으로 추정할 수 있으므로 재사용하거나 임의로 수정하지 않습니다.
9. 사용자의 기존 변경이나 팀원 커밋을 임의로 되돌리지 않습니다.

## 5. 현재 진행 상태

가장 최근 작업 사이클은 사용자가 앱을 실제로 써보면서 짚은 문제들을 코드로 확인하고 고치는 흐름이었습니다. 상세 배경·판단 근거는 [TASKS.md](TASKS.md)의 "최근 완료" 10개 항목이 이 문서보다 훨씬 구체적이니 그쪽을 우선 읽습니다. 여기서는 다음에 이어받을 사람이 알아야 할 상태만 요약합니다.

**이번 사이클에서 실제로 고친 것 (모두 `develop` 병합·검증·학교 서버 배포까지 완료):**
- 화분·베란다 공간은 물주기 기능 자체가 막혀 있던 결함(프론트·백엔드 모두)을 고쳐 텃밭과 동일하게 동작
- 재배 일정 완료 버튼과 그 외 저장/삭제/토글류 액션 9곳에 있던 더블클릭 경합(빠른 연속 클릭 시 옛 버전으로 중복 요청 → 412 충돌 배너)을 `useRef` 동기 잠금으로 전수 수정
- 헤더 네비게이션 위치가 페이지마다 흔들리던 문제, 로고 클릭이 로비로 바로 안 가던 문제, 중복이던 돋보기 버튼 제거
- 시즌 등록 시 작물의 권장 심기·수확 기간을 버튼 한 번으로 바로 채우는 기능(`suggestSeasonPeriodForCrop`), 작물 배치 화면에서도 같은 방식으로 시즌 기간을 그 자리에서 바로 수정하는 기능(`suggestSeasonPeriodCoveringCrops`)
- 공간·시즌 삭제가 막힐 때 "먼저 지워야 하는 대상" 화면으로 바로 가는 링크 추가
- `CultivationTask`·`CultivationRecord`·`WateringSchedule`·`SpaceMemo`에 전용 Policy를 만들어 소유권 인가 구조를 `GrowingSeasonPolicy`와 통일, 본문 검증 엔드포인트의 인가 체크를 모두 `FormRequest::authorize()`로 통일
- 관리자 콘솔 작물 카탈로그·회원 목록 테스트 공백을 채움(코드 변경 없음, 테스트만 추가)
- 결제 연체(`past_due`) 구독이 스케줄러 조회에서 영구히 빠져 방치되던 결함을 고치고(3일 간격 최대 3회 재시도, 실패 시 자동 해지+메일), 이전에는 아예 없던 `/admin/subscriptions`(연체 현황) 화면을 추가
- `needs_support=true`인 작물(토마토·오이·고추·강낭콩) 4종에 "지지대 설치하기" 재배 일정 항목을 심는 날 기준으로 자동 생성(재배 일정이 파종·수확 두 단계뿐이라 부족하다는 지적에 대한 대응 — crops.json에 날짜 간격 데이터가 없는 비료·상시 주의사항류는 임의 날짜를 지어내지 않고 그대로 두었음)
- `/plans`(요금제) 화면이 완성돼 있었는데도 인증 사용자 UI 어디에도 링크가 없어 발견 불가능했던 문제 — 헤더 네비게이션에 "요금제" 항목 추가

**의도적으로 보류한 것:** 결제(구독)를 실제로 쓸 사용자가 있을지 불확실한 상태에서 광고 삽입이나 새 유료 기능 게이팅을 만드는 건 사용자 본인이 "실제 사용자가 생기고 나서 다시 논의" 하기로 결정해 이번 사이클에서는 진행하지 않았습니다. `/plans` 발견 가능성만 먼저 해결한 상태입니다.

**로컬에 남은 미완성 변경은 없습니다** — 위 항목 전부 `develop`에 병합·푸시됐고 학교 서버(`wa26b02`)에도 배포·스모크 테스트를 마쳤습니다. 다만 위 "1. 한눈에 보는 현재 상태"에 적었듯 **실제 운영 백엔드(닷홈)에 이 변경들이 반영됐는지는 확인하지 않았습니다** — 이어받는 사람이 가장 먼저 확인해야 할 부분입니다.

## 6. 디자인 작업 순서 관리

현재 순서와 상태는 [작업 목록](TASKS.md)만 갱신합니다. 완료된 항목을 이 문서의 “남은 작업”으로 중복 유지하지 않습니다.

## 7. 디자인 방향

- 요약 화면: 사진 또는 짙은 숲색 현황 패널을 상단에 두고 핵심 수치를 오른쪽에 배치합니다.
- 관리 화면: 따뜻한 흰색 배경, 얇은 경계, 에메랄드 CTA, 20~24px 반경의 카드로 구성합니다.
- 데스크톱: 정보와 작업을 2~3열로 나누되 제목이나 설명을 덮는 절대 배치를 사용하지 않습니다.
- 모바일: 모든 최소 너비를 해제하고 핵심 입력·작업을 먼저 보여 준 뒤 요약·보조 정보를 아래에 둡니다.
- 빈 상태: 오류처럼 빨간 문구만 보여 주지 않고, 사용자가 무엇을 먼저 해야 하는지와 이동 버튼을 제공합니다.
- 작물 이미지: `public/figma`의 기존 사진을 우선 사용합니다. 없는 작물은 카테고리 색과 한글 첫 글자로 대체하며 임의의 외부 이미지를 추가하지 않습니다.
- 이모지 아이콘과 임의 SVG path를 추가하지 않습니다.
- 화분·베란다에는 격자 UI를 적용하지 않습니다.
- 원본 디자인의 영문 회사 정보·가짜 SNS·가짜 기능은 그대로 복제하지 않고 실제 심어봄 정보와 기능으로 치환합니다.

## 8. 코드 작업 원칙

- 새 유틸·타입·도우미를 만들기 전에 동일 역할이 있는지 `rg`로 검색합니다.
- 도메인 규칙은 `features/<domain>/domain`, API 통신은 `infrastructure`, 서버 상태는 `hooks`, 화면은 `components` 경계를 유지합니다.
- 오류를 빈 배열이나 성공 상태로 숨기지 않습니다.
- `as any`, `as unknown`, 빈 `catch`, 내부 구현을 과도하게 mock한 테스트를 추가하지 않습니다.
- 복잡도와 중첩을 줄이기 위해 guard clause와 작은 렌더링 컴포넌트를 사용합니다.
- 임시 미리보기 라우트와 로컬 스크린샷은 커밋하지 않습니다.
- 사용자 기능 동작을 바꾸지 않은 디자인 작업은 기존 행동 테스트를 유지하고 전체 회귀 검증으로 확인합니다.

## 10. 배포와 운영 주의

- `develop` push 후 Vercel 프론트가 자동 배포됩니다.
- 닷홈 백엔드는 자동 배포가 아닙니다.
- 백엔드 변경이 없으면 FileZilla 업로드나 운영 마이그레이션을 하지 않습니다.
- 백엔드 변경이 있으면 로컬 테스트 후 변경 파일만 업로드하고, 필요한 경우 일회용 실행 파일로 `config:clear`와 `migrate --force`를 실행한 뒤 즉시 삭제합니다.
- 운영 수정 전에 DB 백업과 대상 파일 목록을 확인합니다.
- 운영 `.env`, `public/index.php` 경로 구성과 비밀키를 Git 파일로 덮어쓰지 않습니다.
- 카카오 로그인 운영 반영 파일과 환경 변수·Kakao Developers 설정 순서는 [닷홈 배포 가이드](DOTHOME_DEPLOYMENT.md)의 “카카오 로그인 변경 파일 수동 업로드”를 그대로 따릅니다.
