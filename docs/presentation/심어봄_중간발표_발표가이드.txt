심어봄 중간발표 발표 가이드
발표일: 2026-08-12

1. 발표의 한 문장

“화면만 만든 단계가 아니라, 회원가입부터 재배 기록까지 프론트엔드–Laravel API–MySQL이 연결된 핵심 사용자 흐름을 완성했습니다.”

진행률은 임의의 퍼센트 대신 실제 구현 근거로 설명합니다.

- 프론트 화면 경로 18개
- Laravel api/v1 경로 44개
- 서비스 도메인 테이블 12개
- 프론트 테스트 105개 통과
- 백엔드 테스트 89개, 634 assertions 통과


2. 슬라이드별 발표 문안

01 표지 — 20초
저희 팀은 식물을 처음 키우는 사용자가 재배 공간과 시즌, 작물 배치, 일정과 기록을 한곳에서 관리하도록 돕는 ‘심어봄’을 개발하고 있습니다. 이번 중간발표에서는 디자인 시안보다 실제 데이터가 흐르는 결과물을 중심으로 보여드리겠습니다.

02 현재 상태 — 35초
현재 핵심 사용자 여정은 회원가입부터 공간, 시즌, 배치, 일정·기록·물주기까지 연결되어 있습니다. 구현량은 화면 경로 18개, API 44개, 서비스 테이블 12개이며 자동화 테스트 194개가 통과합니다. 아직 최종 완성은 아니지만, 기능별 화면이 서로 분리된 프로토타입 단계는 넘었습니다.

03 구조 — 40초
프론트는 Next.js가 화면과 입력 검증을 담당하고, Laravel은 인증·권한·업무 규칙을 담당합니다. MySQL은 사용자별 데이터를 관계와 이력으로 보존합니다. 팀원이 같은 DB 구조를 만들 수 있도록 phpMyAdmin 수작업 파일 대신 Laravel 마이그레이션을 단일 기준으로 사용합니다.

04 프론트 진행 상황 — 40초
회원가입과 로그인, 공간·시즌 관리, 격자 배치와 일정·기록·물주기, 대시보드까지 핵심 화면을 구현했습니다. 회원가입에는 이메일 중복 확인, 비밀번호 조건과 확인, 가입 직후 로그인도 반영했습니다. 다음 단계는 모바일 반응형과 접근성, 실제 브라우저 회귀 테스트입니다.

05 백엔드 진행 상황 — 45초
인증, 작물 기준정보, 공간, 시즌, 배치, 일정, 기록, 물주기까지 8개 업무 영역의 API를 구현했습니다. 단순 CRUD뿐 아니라 사용자 소유권, 중복, 기간 겹침, 시즌 범위, 배치 존재 여부를 서버에서 검사합니다. 동시에 수정할 때 데이터를 덮어쓰지 않도록 version과 If-Match도 적용했습니다.

06 ERD — 55초
ERD는 users에서 growing_spaces, growing_seasons로 이어지는 축을 중심으로 읽습니다. 시즌에는 텃밭 배치 하나가 연결되고, 셀별 작물은 별도 테이블에 저장됩니다. 재배 일정과 기록은 시즌 단위로 저장합니다. 물주기는 일정, 완료 기록, 미루기 기록을 분리해 사용자의 과거 행동을 남깁니다. Laravel 내부 관리용 테이블은 발표 가독성을 위해 생략했습니다.

07 시연 계획 — 약 6분
아래 ‘3. 실제 시연 순서’에 따라 진행합니다.

08 문제점과 해결 과정 — 1분 20초
첫째, localStorage 중심 구현은 팀원마다 데이터가 달랐습니다. Laravel API와 MySQL, 마이그레이션으로 공동 구조를 만들었습니다.
둘째, Sanctum 세션에서 프론트 포트와 stateful 도메인이 맞지 않아 가입·로그인이 실패했습니다. 개발 포트를 3000과 8000으로 고정하고 세션 설정과 가입 직후 현재 사용자 확인을 맞췄습니다.
셋째, 전역 링크 CSS가 버튼 글자색을 덮어 초록 버튼의 글자가 검게 보이거나 흰 배경에서 사라졌습니다. Tailwind base 계층으로 이동하고 주요 버튼의 흰 글자를 명시했습니다.
넷째, 브랜치 삭제와 작업 기준 혼선이 있었습니다. 팀원 브랜치는 보호하고 기능 브랜치에서 작업한 뒤 develop에 병합하는 규칙으로 정리했습니다.

09 세부 일정 — 40초
이 일정은 현재 기준 제안 일정입니다. 중간발표 피드백을 반영한 뒤 핵심 흐름 E2E 테스트, 계정·권한 보완, 닷홈 배포, 반응형·접근성·성능, 최종 회귀 테스트와 시연 연습 순서로 진행합니다. 실제 최종 발표일이 달라지면 날짜가 아니라 작업 순서를 유지해 조정합니다.

10 마무리 — 20초
현재 핵심 흐름과 서버 업무 제약, 공통 디자인을 확보했습니다. 이후에는 무리하게 기능 수를 늘리기보다 배포 환경에서 동일하게 동작하는지, 모바일과 접근성이 확보되는지, 최종 시연을 중단 없이 완주하는지를 완료 기준으로 삼겠습니다.


3. 실제 시연 순서

권장 시연 시간: 6분

0:00–0:45 회원가입
- 새로운 이메일을 입력합니다.
- 이메일 사용 가능 표시와 비밀번호 조건, 비밀번호 일치 표시를 보여줍니다.
- 가입 후 로그인 화면을 거치지 않고 앱으로 이동하는 것을 보여줍니다.

0:45–1:30 공간 등록
- ‘첫 공간 등록하기’를 누릅니다.
- 공간 종류, 햇빛, 크기, 지역을 입력해 저장합니다.
- 공간 목록에 저장된 값이 표시되는 것을 확인합니다.

1:30–2:10 시즌 생성
- 방금 만든 공간을 선택합니다.
- 시즌 이름, 시작일, 종료일과 대표 작물을 입력합니다.
- 기간이 잘못되거나 기존 시즌과 겹치면 서버가 거부한다는 점은 설명만 하고, 시연에서는 정상 값으로 저장합니다.

2:10–3:10 작물 배치
- 텃밭 격자를 생성합니다.
- 2종 이상의 작물을 몇 칸에 배치합니다.
- 포기 수와 간격·시기 경고가 계산되는 것을 보여줍니다.

3:10–4:10 재배 일정
- 현재 배치를 기준으로 일정을 생성합니다.
- 일정 한 건의 완료/대기 상태를 변경합니다.
- 홈의 다가오는 일정에 반영되는 것을 보여줍니다.

4:10–5:05 물주기
- 물주기 일정을 확인합니다.
- 한 건은 완료하고, 가능하면 다른 건은 미루기로 변경합니다.
- 완료 기록 또는 미루기 이력이 남는 것을 확인합니다.

5:05–5:50 재배 기록
- 파종·관찰·수확 중 하나의 기록을 입력합니다.
- 날짜, 메모, 선택적 수량과 단위를 저장합니다.
- 기록 화면에서 최신순으로 보이는 것을 확인합니다.

5:50–6:00 대시보드
- 완성 데이터가 있는 백업 계정으로 전환하거나 미리 열린 탭을 사용합니다.
- 공간·시즌·작물 배치 수와 다가오는 일정이 실제 데이터로 계산됐음을 보여주고 마칩니다.


4. 시연 직전 체크리스트

- Laragon에서 Apache/Nginx와 MySQL이 실행 중인지 확인
- backend에서 php artisan migrate:status 확인
- backend 서버: http://127.0.0.1:8000
- frontend 서버: http://localhost:3000
- http://127.0.0.1:8000/api/v1/health 정상 응답 확인
- 새 회원가입용 이메일 하나 준비
- 공간·시즌·배치·일정·기록이 모두 들어 있는 백업 계정 준비
- 브라우저 자동완성·번역 팝업·개발자 오류 오버레이 정리
- 발표용 탭 순서를 홈 → 앱 → ERD 순서로 정리
- 핵심 화면 캡처를 오프라인 폴더에도 보관
- 6분 타이머로 한 번 이상 리허설

중요: Next.js 개발 서버가 이미 실행 중이라는 메시지가 나오면 새 서버를 또 실행하지 않습니다. 표시된 PID를 확인하고 기존 서버 주소를 사용하거나 taskkill /PID <번호> /F로 종료한 뒤 3000 포트로 다시 실행합니다.


5. 발생 가능한 시연 문제와 대응

로그인 또는 회원가입 실패
- 프론트 주소가 반드시 localhost:3000인지 확인합니다.
- 백엔드 8000과 MySQL 실행 여부를 확인합니다.
- 실패가 계속되면 백업 계정이 로그인된 탭으로 전환하고, 원인은 발표 후 확인한다고 짧게 말합니다.

API Failed to fetch
- 먼저 /api/v1/health를 확인합니다.
- 백엔드 서버가 꺼져 있으면 실행합니다.
- 서버 재시작에 시간이 걸리면 캡처 화면과 ERD 설명으로 전환합니다.

데이터 입력이 오래 걸림
- 새 계정 시연은 회원가입과 공간 등록까지만 진행합니다.
- 시즌 이후 흐름은 완성 데이터 계정으로 전환합니다.

예상치 못한 화면 오류
- 같은 동작을 반복 클릭하지 않습니다.
- 준비한 캡처로 전환하고, 구현된 API 테스트 결과와 데이터 구조를 설명합니다.

7. 예상 질문과 짧은 답변

Q. 왜 Laravel을 사용했나요?
A. 인증·권한과 데이터 검증을 프론트에서 분리하고, 마이그레이션으로 팀원이 같은 DB 구조를 재현하며, 공간·시즌·기록의 관계를 서버에서 보장하기 위해 사용했습니다.

Q. 마이그레이션과 phpMyAdmin 가져오기의 차이는 무엇인가요?
A. phpMyAdmin 가져오기는 특정 시점의 DB 복사본이고, 마이그레이션은 변경 이력이 코드로 남는 재현 가능한 설계도입니다. 팀 개발과 배포에서는 마이그레이션을 기준으로 사용합니다.

Q. 현재 완성되지 않은 부분은 무엇인가요?
A. 핵심 기능 연결은 완료했지만 닷홈 운영 배포, 모바일·접근성, 브라우저 E2E 회귀 테스트, 계정 관리 세부 기능은 추가 검증과 보완이 필요합니다.

Q. 데이터가 동시에 수정되면 어떻게 하나요?
A. 수정 가능한 주요 데이터에 version을 두고, 클라이언트가 If-Match로 현재 버전을 보내도록 했습니다. 오래된 화면에서 수정하면 서버가 충돌로 거부해 조용히 덮어쓰지 않습니다.

Q. ERD에서 Laravel 테이블이 왜 없나요?
A. 발표용 ERD에는 서비스 기능을 설명하는 12개 도메인 테이블만 표시했습니다. cache, jobs, sessions, personal_access_tokens 같은 프레임워크 관리용 테이블은 실제 마이그레이션에는 있지만 가독성을 위해 생략했습니다.
